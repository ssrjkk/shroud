# Cryptography & Parameters

## 1. FHE layer

| Parameter | Value | Notes |
|---|---|---|
| Scheme | TFHE, `tfhe-rs` `ServerKey::default()`-equivalent | programmable bootstraps |
| Ciphertext size | 1 792 B (`u32` params, N = 2 000) | see `tfhe::short_integer::parameters` |
| Batching (Bleve) | 8 lanes/ct | amortises 8 NTT bootstraps into 1 |
| Message | 32 bits plaintext × 8 lanes | |
| Noise budget | 40 safe bits | consumed ≈ 3 bits/bootstrapped add |
| Plaintext modulus | 2 64 (for the matmul accumulator) | q = 2 64, so `∑ ≤ 2^40` rows before overflow |
| Bootstraps per epoch (33×d linear) | ≈ 2 600 | measured `node/benches/epoch.rs` |
| Wall clock per epoch, 8-core AVX2 | ≈ 41 s | measured, single shard set of 1 000 rows |

**Scaling guard.** A bootstrapped SIMD add over 8 lanes on one AVX2 core ≈ 12 ms. A 33-lane
dot product is 33 chained adds ⇒ ~400 ms; SGD over a 1 000-row dataset = 1 000 dot products
= ~7 min/epoch. Shroud therefore trains **full-batch or minibatch-of-8 with
gradient accumulation**, i.e. 1 bootstrap-set per minibatch, and *not* per-sample SGD.
This is stated in the buyer-facing model spec as `update_mode: "batch"|"minibatch"`.

## 2. Quantisation

```
u32_lane = clamp( round( x_lane * SCALE ), 0, 2^32-1 ),  SCALE = 1e4
x_hat    = u32_lane / SCALE
```

Rescaling back before output is a *linear* map, so the committee decrypts `u32` lanes and
the buyer multiplies by `1/SCALE` itself. No FHE-side fixed-point arithmetic needed, and
the STARK trace stays in `u32` fields.

## 3. Hashing

| Use | Function | Rationale |
|---|---|---|
| DA object addressing | SHA-256 (BLAKE3 in node for speed, SHA-256 for the on-chain pin) | Ethereum-native |
| `ctRoot` | incremental SHA-256 over `(shardCid ‖ leafIndex)` sorted ascending | cheap, recomputable by all nodes |
| STARK transcript | Winterfell Fiat–Shamir (Poseidon2, 8-byte field elements) | domain separated from SHA-256 |
| Row shape proof | Poseidon2 over `(salt, label, lanes, scale)` | cheap inside a Groth16 circuit |
| EIP-712 binding | `keccak256` | ERC-712 standard |
| Key pinning | `keccak256(abi.encode(s_pub))` on chain | ERC-7684 style pinning |

## 4. Key management

```
DKG (n=7 committee, t=4, Pedersen DKG over BLS12-381 / BN254)

  each member i  samples poly f_i(x) = a_i + b_i x + ... + b_{t-1} x^{t-1}
  broadcast commitments  C_j^k = commit_0(f_i(j))  for j in 0..n-1
  VSS check  (via 2-party ECDH re-encryption handshake, so members learn no plaintext share)
  complaints  ->  DISQUALIFIED[i], keygen retries with the reduced set
  output      s_pub = TFHE key derived from s = Σ f_i(0)
                shares  (i, f(i))  held encrypted-at-rest on each member
```

- `s` is **never** reconstructed. Decryption of ciphertext `c` with share set `S` (|S| ≥ t):

  ```
  partial_i = Decrypt(c, s_i = f(i))                 # each member returns 32 B
  plaintext = Combine_Lagrange({ (i, partial_i) })  # contract-side, ≥ t of them
  ```

- Committee members are bound by an on-chain `CommitteeMember` registry with a bond, and
  sign reveal requests in BLS. Removing a member requires a new DKG round
  (`NetworkParams.rotate()`), which re-encrypts nothing — old ciphertexts stay readable by
  the old key only if the old key shares are preserved, so rotation *retires* old ability
  to decrypt. That is deliberate: revealability of past outputs is desired, decryptability of
  *new* rows under a new key is not shared with the old committee.

## 5. ZK layer

| Proof | System | Size | Verify | Purpose |
|---|---|---|---|---|
| "I have a valid row" | Groth16 (BN254) | 128 B | ~300 k gas, 1.2 ms | anti-poisoning of contributions |
| "I computed this epoch honestly" | **ZK-STARK (Winterfell, Binius/BabyBear field)** | ≤ 48 KB | off-chain precompile + on-chain `ProofVerifier` | proof of compute |
| "t committee members agree to reveal" | BLS signature aggregation | 96 B | 1 pairing | gating threshold decryption |

### 5.1 Why a STARK and not a SNARK

The PoC trace is 2^20 BabyBear elements generated by ~10^9 FHE field operations. A SNARK
would need either a trusted setup proportional to the trace or a R1CS that cannot express
the hash-chain efficiently. A STARK gives 128-bit security with no setup, ~1.5 s prove and
~8 ms verify on a modern core — the right trade for a 41 s epoch.

The honest caveat: we do **not** prove the FHE internals inside the STARK (see
`05-honest-limitations.md`). We prove the *cleartext* linear-algebra trace whose inputs are
the ciphertext digests the prover must have loaded, and the honesty of the FHE layer is
guaranteed by the dispute/reexecution quorum. This is an explicit protocol design choice,
not an oversight.
